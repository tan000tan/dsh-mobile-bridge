# 审批机制专项审计（阶段二 · 第二阶段）

审计时间：2026-10-24。方法：完整调用路径的源码追踪（手机端 fork + 官方 0.2.1-rc.3 源码 + 本机 0.1.7-rc.2 安装包 grep 取证）+ mock-harness 专项测试（真实 socket）。每一结论附证据文件路径。

## 一、十步调用路径追踪（全部有源码证据）

| # | 环节 | 结论与证据 |
|---|---|---|
| 1 | DSH 创建审批请求 | DSH 进程内 approval 缝：敏感工具动作请求一次性决策；策略 ask（默认，走 answerer waterfall）/never（确定性拒绝）；**无 answerer 时 fail-closed 返回 unavailable**；只有 allowed-once 语义。证据：官方仓库 `packages\interaction\user-approval\README.md`、`docs\subsystems\permission-presets.md` |
| 2 | 审批请求传输到手机 | `approval/request` 属主机 Cordis waterfall，经 `API_REMOTE_FORWARDED_EVENTS` 白名单转发到 `$events` 流；**本机 0.1.7-rc.2 安装包 grep 实证**：`dsh-api-remotes\lib\index.js` 中存在 `approval/request` 与 `api-session/error` 等同名事件串（逐字命中） |
| 3 | 手机端注册请求 | fork `app\...\data\SessionStore.kt:1178-1198` `handleApprovalRequested`：按 waterfall 帧的 `eventId` 注册进 `approvalRequests`，会话行标记 pending，UI 出审批卡（approvalId=eventId，0.1.2 起无独立 approvalId） |
| 4 | 手机点击批准发出的实际请求 | `SessionStore.respondApproval`（:2020-2041）→ `api.answerEvent`（core `DshApiClient.kt:931-942`）→ **`POST /api/$events/result`**，body `{"args":{"clientId":"<当前连接代>","eventId":"<审批请求id>","outcome":{"kind":"result","value":"allowed-once"}}}`（信封 type=client-request） |
| 5 | 手机点击拒绝发出的实际请求 | 同一端点同一信封，`value:"rejected"`（`ApprovalOutcome.REJECTED`，core `StreamProtocol.kt:447-450`）。补充说明走另一通道：`answerQuestions`（同端点，value=完整答案对象）或 `session/updateQueue`（steer 队列） |
| 6 | 请求返回 DSH | 网关 `judgeEventResult` 语义（官方 `packages\api\gateway`）：校验 `args` 信封 → **clientId 必须是当前 owner 连接代** → 按 `eventId` 关联到 pending waterfall → waterfall 的返回值即 outcome |
| 7 | 关联到真实待审批操作 | 双重关联：客户端先查本地注册表（无此 eventId → `Refused(NOT_PENDING)`，不发包）；主机按 eventId 关联 waterfall（`SessionStore.kt:2032` 注释与 mock `judgeEventResult` 同构实现） |
| 8 | 审批结果如何影响执行 | 官方语义：allowed-once 授权**一次**操作；rejected 使其后的工具调用保持 blocked；`approval/asked|decided` 写入会话审计日志（log-only）。证据：官方 `packages\interaction\user-approval\README.md` |
| 9 | 失败/超时/断开/过期 | `answerOutcome`（SessionStore.kt:2153-2178）：传输层失败 → `Unsent`（**不伪造成功**，审批卡保留）；主机明确 ok:false → `Refused(主机错误码)`；仅 Accepted 才从注册表遗忘该请求。过期/代际不符：主机拒绝（`stale-generation`）+ 客户端 `an answer from a retired generation is refused` 测试在位（ProtocolEndToEndTest）。pending 审批是主机进程内存态，跨重启不恢复（官方文档明示） |
| 10 | 是否存在"手机显示批准成功、电脑端实际未批准" | **未发现该路径**。`QuestionOutcome.Accepted` 仅在 `RpcResult.Ok`（主机应答信封）时返回；本地不存在"点了就成功"的分支。反向风险（主机收不到应答）表现为 Unsent/Refused 并保留审批卡 |

## 二、三层机制的严格区分（审计核心结论）

| 层 | 是什么 | 证据 |
|---|---|---|
| A. 手机端咨询性风险提示（本项目新增） | 发送任务前的本地关键词启发式弹窗，**不是安全机制**，会漏报误报 | `RiskAdvisory.kt` 纯本地函数、无网络；文案明示"电脑端审批才是真正的执行边界" |
| B. 手机端对 DSH 原生审批请求的响应 | 把用户的批准/拒绝**如实回传**到 DSH 进程内 approval 缝的通道（本节第一部分） | 见上表 4-7 |
| C. 真正约束工具执行的安全机制 | **DSH 进程内的 approval 缝**（fail-closed、allowed-once、审计日志）+ 沙箱模式 | 官方 `packages\interaction\user-approval\README.md`、`SAFETY.md`（"沙箱、审批提示、权限控制降低风险但不保证隔离"） |

**明确声明**：本项目没有、也不应声称"所有高风险操作都受手机端额外确认保护"。B 通道的价值在于"用户不在电脑前时仍能响应 DSH 真实审批"，其安全性完全继承 C 层。

## 三、专项测试（真实 socket，mock-harness 扮演主机；已于 2026-10-24 实际执行通过）

新增 `app\src\test\java\com\labteto\dshmobile\connection\ApprovalAuditTest.kt`（4 项）+ mock 端新增 `eventAnswers` 记录（记录主机实际收到的线上对象，仅加列表不改行为）。

**执行方式说明（如实记录）**：Gradle 测试工作进程（JDK17）在中文路径下存在 @argfile 以系统 GBK 解码 UTF-8 路径的启动器层限制，导致首次尝试出现全类 ClassNotFoundException（环境问题，非被测代码问题）。最终以绕过方案完成真实执行：`gradle :mock-harness:jar` 重打包 → init 脚本导出测试运行时 classpath → **JDK25 直接以 JUnitCore 执行**（argfile 以 GBK 编码写入，工具与过程文件在 `自动化测试与测试结果\` 与 `临时文件与构建缓存\`），运行目录为 fork 根。结果：**OK (4 tests)**，原始输出存档 `临时文件与构建缓存\审批测试直跑输出.txt`；同一通道全量回归 OK (411 tests)（`自动化测试与测试结果\阶段二_全量回归直跑输出.txt`）。

| 用例 | 断言 | 结果 |
|---|---|---|
| 批准以 allowed-once 且携带正确关联字段到达主机 | 主机记录 clientId=当前代、eventId、kind=result、value=allowed-once | ✅ 实测通过 |
| 拒绝以 rejected 到达主机且不携带允许值 | value=rejected、eventId 正确 | ✅ 实测通过 |
| 对未决事件 id 的应答不得影响已记录的其他应答 | 幽灵应答独立成条，不覆盖 evt-real 的合法应答 | ✅ 实测通过 |
| 代际不匹配的应答被网关拒绝（stale-generation） | RpcResult.Err 且不进入主机记录 | ✅ 实测通过 |

既有测试对本清单其余项的覆盖（引用，未重写）：

- 重复响应：客户端注册表结算后遗忘（RequestSettlementTest `an accepted answer ends the request`）+ respondApproval 无待批返回 `Refused(NOT_PENDING)` 不再发包（SessionStore.kt:2031-2037 源码路径）。
- 断开不伪造成功：RequestSettlementTest `a response that never arrived keeps the card`；respondApproval 无连接返回 `Unsent`。
- 不支持审批场景 fail-safe：主机无 $events/result 时传输失败 → Unsent（answerOutcome 传输层分支）；DSH 侧无 answerer 时 fail-closed（官方文档）。
- 线上形状回归：`PinnedProtocolFixtureTest` 钉住真实 harness 提交的协议夹具（4878cda/5badb15.json）；`QuestionResponseEncodingTest` 钉住应答编码。

## 四、遗留限制（如实声明）

1. mock 不具备工具执行语义，"批准后工具真实执行/拒绝后工具真实被挡"的**端到端**验证需要真实 DSH（列为需授权项）；本审计证明到"正确的值+正确的关联字段到达主机网关"这一层。
2. 审批请求仅在 open turn 内有效且为主机内存态：手机端离线期间的审批请求会随主机结算消失（官方语义），重启后无需也无法补答——UI 以审批卡消失如实呈现。
